# M19 — Medicine tracker

> **Status: IMPLEMENTING — partial delivery; reliability follow-up implemented, native and human validation pending.**
> Numbered M19 because **M18 is the active calendar-reliability repair**. See
> §0 for the prerequisite that gates any M19 implementation work.

Canonical plan for M19. Adds a **treatment / medicine / dose** model to
Attention Hub: a finite course of medicines you have to take on a schedule,
surfaced in Today between meetings and to-dos, with its own optional widget
destination segment, an anchored popup, and a manager window.

It is deliberately **not** built on to-dos. A to-do is something you decide to
do once; a dose is a planned occurrence generated by a rule, and it is either
taken, skipped, or missed. Mixing them would make the to-do model carry
recurrence, a second completion vocabulary, and health data it should not hold.

## 0. Prerequisite — M18 must be checkpointed first

**No M19 implementation begins until the M18 calendar-reliability repair has
been tested and checkpointed.** Concretely, all of the following must hold
before PR 1 of this plan is opened:

1. The M18 repair has been **human-tested** on an installed build, with its
   calendar-reliability checks signed off through its own review launcher.
2. `pnpm test`, `pnpm build`, `cargo test`, strict Clippy, and `cargo fmt` are
   **green** on that tree.
3. That state is **committed**, so M19 branches from a known-good commit and
   has a clean point to revert to.

**A tag is required only if that checkpoint is released.** An unreleased
internal checkpoint needs a commit, not a version tag — tagging every
intermediate repair would inflate the release history with builds no user ever
receives.

M19 touches the widget width math, the Today popup, and the widget's polling
loop — three things the calendar repair also lives near. Branching M19 off an
untested M18 tree would make any regression ambiguous between the two
milestones, which is precisely the cost this prerequisite avoids.

## Decisions locked

| Question | Decision |
| --- | --- |
| Storage | A **separate** `medicine.json`, schema version 1, created lazily on first mutation, using the existing `local_store` atomic-write + bounded-backup pattern. Not part of `workspace.json`. |
| Why separate | Health data must not ride along in workspace export, must not share the to-do store, and must be able to evolve its schema without touching the workspace version guard. |
| Internal entities | `Treatment`, `Medicine`, `Dose`. User-facing words are the same three. |
| Dose history | **Materialized planned occurrences.** Every planned dose is a stored row, written when the schedule is created or edited. Not derived on read. |
| Schedule edits | Apply to **future untouched occurrences only**. Past occurrences and any occurrence that was taken, skipped, or notified are frozen (§1b). |
| Treatment span | **Finite in V1.** `startOn` and `endOn` are both required on treatments and on medicines. |
| Medicine window | The treatment range is **derived** from the earliest start and latest end of its medicines, so containment holds by construction (§1e). Supersedes the original containment-with-rejection rule. |
| Scheduling | Fixed local **times of day**, plus a **day pattern**: every day, every N days, or selected weekdays. Nothing else in V1. |
| Deferred schedules | Open-ended courses, as-needed (PRN), every-N-hours interval dosing, and tapering. All out of V1 (§10). |
| Slot times | Local wall-clock `HH:MM`, not instants. `08:00` means 08:00 wherever you are. This is the opposite call from `remindAt` and it is intentional. |
| Slot storage | **Civil** `(slotDay, slotTime)` for storage, generation, identity, and ordering. Exactly one occurrence per local slot on DST transition days (§1h). |
| Elapsed time | Resolved to a **deterministic local instant** for `doseState`, notification grace, and the schedule-edit cutoff. Ambiguous → **earlier** occurrence; nonexistent → **first valid instant after the gap boundary** (02:30 → 03:00, and all skipped times collapse there); future slots resolved in the **current** zone. Never stored (§1h). |
| Widget scope | Badge, left count, and `data-due` cover **only `slotDay === today`**. Older missed doses appear in Recent alone and never hold the widget highlighted (§4a). |
| Preference contract | `showMedicinePanel` — type, default off, normalization, change event, tests — lands in **checkpoint 1**. The manager control reads and writes it in 2; the **widget** starts consuming it in 4 (§7). |
| Human testing | The checklist **never** mutates the tester's system clock or timezone. DST is covered by deterministic fixtures (§7, §8). |
| Descriptive metadata | Name, strength, form, amount, and food rule apply **retroactively to displayed history**. A genuine regimen change must create a **new Medicine entry** (§1b). |
| Today order | **Events → Medicine → To-dos.** |
| File size limit | The existing `local_store::MAX_FILE_BYTES` (4 MiB), reused as-is, with medicine-specific error wording. The **prospective serialized check is authoritative**; the 10 000 occurrence cap is a logical limit, not a size guarantee (§1g). |
| Reclaiming space | **Delete a completed or archived treatment** after revision-guarded preflight. There is no `clear_treatment_dose_history` (§3). |
| Popup bounds | 8 total visible dose rows and 3 treatment headings, with `+N more` opening the manager (§4b). |
| Reminders | Widget polls; the Rust command sends the toast. One shot per occurrence, guarded by `notifiedAt`, and **only inside the configured grace window** (§5). Off by default. |
| Grace window | **One shared 15–240 minute preference** driving both the `due`/`missed` split and notification eligibility (§5). |
| Notification text | Generic. Neither the title nor the body names a medicine (§5). |
| Widget visibility | `showMedicinePanel` default **off**, with a **Show in widget** control in the Medicine manager header mirrored under **Advanced → General → Visible panels**. No one-time-hint state (§11.5). |
| Advanced placement | **General / Visible panels**: Show in widget. **Reminders**: dose notifications, grace window, and the medicine data panel (§4g). |
| Taskbar mirrors | No geometry change. Mirrors self-correct from measured DOM rectangles; only a resize-alignment regression check is required (§4a). |
| At-rest protection | None beyond the Windows user profile. The file is local plaintext (§6). |
| Export / import | Not in M19. Requires merge semantics first (§10). |
| Manager V1 scope | Schedule, Today, Notes, and a simple **Recent** list. The 30-day history matrix is deferred (§4c). |
| Delivery | Five **implementation checkpoints**, which may be five PRs or five commits on one branch, provided each independently passes its gates (§7). |
| Medical logic | Out of scope permanently: no dosage validation, no interaction checks, no drug database, no network. A personal log, not medical advice. |

## Naming

Spell it **Treatment**, **Medicine**, and **Dose** in UI copy, docs, and
release notes. Store keys are `treatments`, `medicines`, `doses`; commands use
`treatment`, `medicine`, `dose`. The manager window label is `medicine`; the
popup is `medicine-panel`. "Pill" never appears in UI copy — not every medicine
is a pill.

## 1. Data model

Single file: `%APPDATA%/<bundle>/medicine.json`, plus `medicine.backup.json`
and `medicine.pending.json` through the existing
[local_store.rs](../../src-tauri/src/local_store.rs) pattern.

```jsonc
{
  "schemaVersion": 1,
  "revision": 0,                      // monotonic; +1 per successful mutation

  "treatments": [
    { "id", "name",                   // "Sinusitis — September"
      "notes": [NoteSegment], "notesRevision",
      "startOn": "YYYY-MM-DD",        // required
      "endOn": "YYYY-MM-DD",          // required, >= startOn
      "completedAt": null,            // finished early, by hand
      "archivedAt": null,
      "sortIndex", "createdAt", "updatedAt" }
  ],

  "medicines": [
    { "id", "treatmentId",
      "name",                         // "Amoxicillin"
      "strength",                     // "500 mg" — display only
      "form": "tablet" | "capsule" | "drops" | "spray" | "syrup" | "injection" | "other",
      "doseAmount",                   // "1", "1.5", "2" — display only
      "foodRule": "any" | "before" | "with" | "after",
      "times": ["08:00", "20:00"],    // local HH:MM, sorted, unique, non-empty
      "dayPattern": { "kind": "everyDay" }
                  | { "kind": "everyNDays", "interval": 2 }
                  | { "kind": "weekdays", "days": [1, 3, 5] },   // ISO 1=Mon..7=Sun
      "startOn": "YYYY-MM-DD",        // required, within the treatment range
      "endOn": "YYYY-MM-DD",          // required, within the treatment range
      "scheduleRevision": 1,          // bumped only by schedule-affecting edits
      "notes": [NoteSegment],
      "sortIndex", "createdAt", "updatedAt" }
  ],

  "doses": [
    { "medicineId", "slotDay": "YYYY-MM-DD", "slotTime": "HH:MM",
      "scheduleRevision": 1,          // generation that produced this occurrence
      "takenAt": null,                // RFC3339 instant or null
      "skippedAt": null,              // RFC3339 instant or null
      "notifiedAt": null,             // one-shot reminder guard
      "updatedAt" }
  ]
}
```

`NoteSegment` is the existing `{ text, href }` shape; parsing and linkification
reuse [rich-notes.ts](../../src/rich-notes.ts) unchanged.

### 1a. Why occurrences are materialized

The alternative — deriving occurrences from the schedule on every read and
storing only the ones acted on — is cheaper on disk and worse at the one job
this feature has: telling the truth about the past.

| Concern | Materialized | Derived |
| --- | --- | --- |
| Edit a schedule mid-course | History is untouched by construction | Past occurrences silently change or disappear |
| "Was Tuesday's evening dose planned?" | A row answers it | Answer depends on today's schedule |
| Progress denominator | `count(rows)` | Re-derivation, must exclude retired slots by hand |
| Reminder query | Filter stored rows | Schedule expansion duplicated in Rust |
| Missed doses | A row with no timestamps | Absence of a row, indistinguishable from "not planned" |

That last line is decisive. In a sparse log, "missed" and "never scheduled" are
the same absence, and you have to re-derive the schedule to tell them apart —
which fails as soon as the schedule has been edited since.

The cost is disk size and a regeneration step, both bounded by §1g and V1's
finite treatments.

**Generation is authoritative in Rust**, because Rust owns writes.
`medicine-model.ts` keeps a *preview* expansion used only to show
"21 doses over 7 days" in the editor before saving, and to disable Save on an
invalid window. Both implementations are asserted against one shared case
table (§8) so the preview cannot promise something the store will not produce.

### 1b. Regeneration: future untouched only

An occurrence is:

- **touched** — any of `takenAt`, `skippedAt`, `notifiedAt` is non-null;
- **past** — its **resolved local instant** is at or before the edit instant
  `T`, both resolved by the policies in §1h;
- **frozen** — touched **or** past;
- **regenerable** — untouched **and** future.

A **schedule-affecting edit** is a change to `times`, `dayPattern`, `startOn`,
or `endOn`. Inside one `mutate` closure it:

1. bumps the medicine's `scheduleRevision`;
2. deletes every **regenerable** occurrence of that medicine;
3. generates occurrences from the new schedule for every slot strictly after
   `T`, skipping any `(slotDay, slotTime)` already held by a frozen occurrence;
4. leaves every frozen occurrence exactly as it is, retaining its older
   `scheduleRevision`.

Consequences worth stating, because they are the point of the design:

- A frozen occurrence at a slot the new schedule no longer contains **stays**
  in history and still counts in progress. It really did happen, or really was
  missed.
- A frozen occurrence at a slot the new schedule still contains is **not
  duplicated**.
- A **past untouched** occurrence is frozen and displays as `missed`. Missed
  doses must remain visible; regenerating over them would erase them.
- Editing `name`, `strength`, `form`, `doseAmount`, `foodRule`, or `notes`
  regenerates **nothing** and does **not** bump `scheduleRevision`.
- Changing a treatment's range regenerates nothing by itself; it is validated
  against its medicines (§1e), and medicine windows are changed through
  medicine edits.

**Descriptive metadata is retroactive, and that is a real limitation.** Because
occurrences carry no denormalized fields (§1c), they render through the
medicine's *current* `name`, `strength`, `form`, `doseAmount`, and `foodRule`.
Editing any of those therefore **rewrites how existing history is displayed**:
rename "Amoxicillin" to "Amoxil" and last week's taken doses will read
"Amoxil". The stored facts — which slot, taken or skipped or missed, and when —
never change, but their labels do.

This is the correct behaviour for a typo, a clarified strength label, or a
brand/generic name correction, which is what these edits are for. It is the
**wrong** behaviour for a genuine regimen change. So:

> **A genuine regimen change must create a new Medicine entry**, not an edit.
> Dropping from 500 mg to 250 mg, or switching to a different drug, means
> ending the current medicine's window and adding a second medicine with the
> new values. Editing `strength` in place would retroactively claim you had
> been taking 250 mg all along.

The manager states this next to the strength and dose-amount fields rather than
leaving the user to discover it, and the review checklist (§7, PR 5) tests it
explicitly. Per-occurrence descriptive snapshots would remove the limitation
but cost the byte budget in §1g, and tapering — the main case that wants
them — is already deferred (§10).

### 1c. Dose identity and row shape

Identity is the composite `(medicineId, slotDay, slotTime)`. No random id:
the slot *is* the identity, which makes generation idempotent and logging
naturally duplicate-proof.

Two deliberate divergences from every other entity in this codebase, both
driven by the byte budget in §1g:

- **No `createdAt`.** A generated occurrence's creation time carries no user
  meaning; `updatedAt` plus the three act timestamps carry everything the UI
  and history need.
- **No denormalized medicine or treatment fields.** Rows join through
  `medicineId`. A cached name on 10 000 rows would cost more than it saves and
  would go stale on rename.

`takenAt` and `skippedAt` are mutually exclusive; setting either clears the
other. Undo clears both.

### 1d. Derived state

Computed in `src/medicine-model.ts`, never stored:

```
doseState(dose, now, graceMinutes)
  -> "taken" | "skipped" | "due" | "missed" | "upcoming"

previewOccurrenceCount(medicineDraft)   // editor only; see §1a
medicineWindowWithinTreatment(draft, treatment)   // editor-side mirror of §1e

treatmentDayProgress(treatment, now)    // { dayIndex, totalDays }
treatmentDoseProgress(treatment, medicines, doses)  // { taken, skipped, planned }
todayDoseRows(snapshot, now)            // sorted by slotTime, then medicine sortIndex
nextDoseAt(snapshot, now)
dueDoseCount(snapshot, now, graceMinutes)
activeTreatments(snapshot, now)         // not archived, not completed, today in range
```

`doseState` reads a stored row, so it is a pure classification with no schedule
expansion in it. The elapsed comparisons below run on the slot's **resolved
local instant** (§1h), because `due` versus `missed` is a statement about
elapsed time and civil arithmetic cannot express it across a DST transition:

| State | Condition |
| --- | --- |
| `taken` | `takenAt != null` |
| `skipped` | `skippedAt != null` |
| `due` | untouched, `resolved(slot) <= now`, and `now − resolved(slot) <= grace` |
| `missed` | untouched, and `now − resolved(slot) > grace` |
| `upcoming` | untouched, `resolved(slot) > now` |

Resolution is read-time and never stored, so a future dose keeps its wall-clock
time after the user changes timezone (§1h).

**Progress semantics.** Because V1 treatments are finite and occurrences are
materialized, both progress figures always have a real denominator. There is no
indeterminate state and no invented total. The bar is **day progress** —
"Day 3 of 10" — with dose counts beside it as text: "2 of 4 taken today",
"18 of 30 taken" for the course.

### 1e. Referential integrity, ranges, and cascades

- A medicine must reference an existing treatment.
- A dose must reference an existing medicine.
- `treatment.startOn <= treatment.endOn`; `medicine.startOn <= medicine.endOn`.
- **The treatment range is derived, not asserted.** A treatment's `startOn` and
  `endOn` are kept equal to the earliest start and latest end of its medicines,
  recomputed in Rust (`sync_treatment_range`) after every medicine create,
  update, move, and delete. Containment therefore holds by construction and
  cannot be violated.

  This **supersedes the earlier containment-with-rejection rule** and the
  §11.1 resolution that went with it. Both assumed the user maintains two
  ranges that must be kept consistent by hand; deriving one from the other
  removes the class of error rather than reporting it. There is no rejection to
  write, no count of blocking medicines to name, and no way for the two to
  disagree.

  Consequences, all intentional:
  - The range a user types when **creating** a treatment seeds the first
    medicine's dates and holds until a medicine exists. From then on it follows
    the medicines.
  - `update_treatment` accepts `startOn`/`endOn` in its input but they are
    overwritten by the derived values whenever the treatment has medicines. The
    manager never offers those fields for an existing treatment — rename edits
    the name alone — so no UI path can type a range that is then discarded.
  - The UI states the rule where the user meets it: *"Dates adjust when you add
    medicines."* on the create form, and *"Course dates come from the earliest
    start and latest end of your medicines."* on the treatment header.
  - Deleting the last medicine leaves the treatment at its final derived range
    rather than restoring the originally typed one.

  The one loose end is that `update_treatment` still takes range fields it may
  ignore. Left as-is because the notes command shares the input shape, but a
  future revision should either reject a differing range or drop the fields.
- Deleting a treatment cascades its medicines and all their occurrences.
- Deleting a medicine cascades all its occurrences, history included.
- Both are revision-guarded and preflighted with counts, reusing the M17
  delete-impact pattern verbatim.
- Archiving or completing a treatment keeps everything, including history, and
  removes it from Today, the widget segment, the popup, and reminders.

### 1f. Lazy creation

Nothing is written at startup. `get_medicine_snapshot` on a missing file
returns an **empty** store in memory and writes nothing. Unlike the workspace
there is no seeded row, so there is no seed-determinism problem to solve — an
in-memory empty store and a written empty store are trivially identical.

### 1g. Limits, and reconciling them with `local_store`

The earlier draft of this plan proposed a 2 MiB medicine-specific cap. That is
withdrawn: [local_store.rs:8](../../src-tauri/src/local_store.rs) already
enforces `MAX_FILE_BYTES = 4 MiB`, applied **per file**, in both `read_file`
and `write`. A second, smaller limit would mean two mechanisms disagreeing
about the same failure. **Reuse the existing 4 MiB mechanism unchanged.**

What does need changing is the wording. Every message in `local_store::write`
is hardcoded with `Workspace` as its subject — "Workspace has reached its 4 MiB
safety limit.", "Workspace could not update its local backup.", and so on.
Surfacing those in the medicine manager would be wrong.

**Fix:** thread a `label: &'static str` through `local_store::write` and
`replace_file`, formatting each message as `{label} …`. `workspace.rs` passes
`"Workspace"` and `medicine.rs` passes `"Medicine"`.

Exactly **nine shipped messages** are in scope, and they were counted rather
than estimated: eight in `write`
([local_store.rs:129–150](../../src-tauri/src/local_store.rs)) plus one in the
Windows `replace_file` ([local_store.rs:207](../../src-tauri/src/local_store.rs)).
All nine already begin with `Workspace` as their grammatical subject, so
`format!("{label} …")` reproduces them **byte-identically** — asserted by a
test, because these strings are user-visible. The two non-Windows
`replace_file` arms carry two more strings and get the same treatment; they are
not in shipped builds.

**`write_portable` stays out of scope.** It is only used by workspace export,
which medicine does not have in V1 (§10), and two of its six messages —
"The export destination directory is unavailable." and "A stale pending
workspace export could not be removed." — are not subject-prefixed, so they
cannot be mechanically relabelled. It passes the literal `"Workspace"` into
`replace_file` and is otherwise untouched. When medicine export arrives, those
two strings get reworded then, deliberately.

`medicine.rs`'s `load()` maps `ReadError` to medicine-worded messages exactly
as `workspace::load` does today. `ReadError` is a label-free enum and needs no
change.

| Entity | Cap |
| --- | --- |
| File | 4 MiB (existing `local_store` mechanism) |
| Treatments | 100 |
| Treatment span | 365 days |
| Medicines per treatment | 30 |
| Medicines total | 500 |
| Times per medicine | 12 |
| Occurrences per medicine | 2 000 |
| Occurrences per treatment | 4 000 |
| **Dose occurrences total** | **10 000** |
| Treatment / medicine name | 80 chars |
| Strength / dose amount | 32 chars |
| `everyNDays.interval` | 2 – 30 |
| `weekdays.days` | non-empty subset of 1 – 7 |
| Notes | 4 000 chars, 256 segments, 25 links (reused) |

#### The 10 000 cap is a logical limit, not a size guarantee

The earlier draft claimed 10 000 rows was "about 2.5 MiB — comfortably inside
4 MiB". **That reasoning was wrong**, and measurement is why. Representative
serialized sizes for the row shape in §1c:

| Content | Serialized size |
| --- | --- |
| 10 000 untouched occurrences | **2.595 MiB** |
| 10 000 touched / notified occurrences | **2.938 MiB** |
| 10 000 occurrences **plus** maximum notes and entity counts | **15.207 MiB** |

These are measured, not estimated: `medicine::tests::byte_budget` builds each
store, serializes it with the same serializer `local_store::write` measures
against, and asserts the conclusions below. The reporting helper that prints
the table is `cargo test -- --ignored --nocapture byte_budget::report`.

Earlier revisions of this table carried 2.689 / 3.109 / 5.812 MiB from a
one-off measurement. The first two were close; **the third was wrong by a
factor of about 2.6**, because it did not scale treatments and medicines to
their own caps at the same time — 100 treatments and 500 medicines each
carrying the full 4 000-character notes ceiling dominate everything else. The
conclusion is unchanged and now holds by a much wider margin.

The third row exceeds 4 MiB nearly four times over. So the occurrence caps and the entity caps in the
table above are individually reasonable but **not jointly bounded** — reaching
several maximums at once produces a file the store will refuse to write.

Therefore:

- **The prospective serialized 4 MiB check is authoritative.** Every mutation
  serializes the candidate store and compares it against
  `local_store::MAX_FILE_BYTES` **before** committing anything, which
  `local_store::write` already does
  ([local_store.rs:132–136](../../src-tauri/src/local_store.rs)). No write
  that would exceed 4 MiB ever lands, regardless of which caps were satisfied.
- **10 000 is retained as a logical cap** — it keeps occurrence counts sane,
  gives a clear early error, and bounds regeneration work. It is a usability
  limit, not a size proof.
- Because the two limits can disagree, the size failure needs its own readable
  message. A user who hits 4 MiB while every logical cap still has headroom
  must be told the file is full and pointed at deleting a finished treatment —
  not shown a cap number that looks satisfied.
- Growth is dominated by notes, not occurrences. Occurrences are the cheap
  part; §1c's dropped `createdAt` and absent denormalized fields are what keep
  them cheap.

For scale, the realistic case is far away from either limit: a 90-day treatment
with four medicines at three times a day is 1 080 occurrences.

Creating or editing a schedule that would exceed any occurrence cap **fails
before writing**, naming the cap it hit. Records are never silently pruned — a
health log that deletes itself is worse than one that says it is full.

**Space is reclaimed by deleting a treatment.** When either limit is reached,
the manager surfaces which **completed or archived** treatments can be deleted,
and deletion goes through the ordinary revision-guarded preflight (§1e), which
reports exactly how many medicines and occurrences will be destroyed before the
user confirms. There is no separate history-clearing command; see §3.

### 1h. Civil storage, resolved instants, and DST

There are two distinct jobs here, and an earlier draft of this plan wrongly
gave both to civil arithmetic. They are separated now.

#### Civil, always: storage, generation, identity, ordering

A slot is a `(slotDay, slotTime)` pair — a bare `YYYY-MM-DD` and a local
wall-clock `HH:MM`. That pair is what is **stored**, what **generation** walks,
what forms the composite **identity** in §1c, and what **orders** rows for
display, compared lexicographically by day then by minutes since midnight.

None of those four jobs needs an instant, and giving them one is what breaks on
a DST transition:

- **Spring forward.** 02:30 does not exist on the transition day. An
  instant-walk yields an error, a silent shift to 03:30, or a shift to 01:30
  depending on the library — so a 02:30 dose vanishes, duplicates, or moves.
- **Fall back.** 01:30 occurs twice. An instant-walk emits the slot twice.

Civil generation sidesteps both. **The generation rule is: exactly one
occurrence per local slot per covered day, on every day including transition
days.** A medicine taken daily at 02:30 gets one occurrence on the
spring-forward day and one on the fall-back day. None skipped, none duplicated.

#### Resolved instants: elapsed time

**Civil arithmetic cannot answer "how long ago was this due."** Between two
civil pairs separated by a DST transition, the wall-clock difference and the
elapsed difference disagree by an hour, and the grace window is a statement
about *elapsed* time. An earlier draft claimed grace could be "computed on the
civil pair as well" and that a `due` state never requires instant resolution.
**Both claims were wrong and are withdrawn.**

Three places need a real instant, and all three resolve the slot the same way:

| Consumer | Why an instant is required |
| --- | --- |
| `doseState` (§1d) | `due` vs `missed` is `now − slot > grace`, an elapsed comparison |
| Notification grace (§5) | Eligibility is `slot <= now <= slot + grace`, elapsed |
| Schedule-edit cutoff (§1b) | `T` must order against slots consistently with the two above |

The resolution function is **deterministic and total** — it returns an instant
for every civil pair, including the two that a naive conversion cannot
represent:

| Case | Policy |
| --- | --- |
| **Ambiguous** (repeated hour, fall back) | Resolve to the **earlier** occurrence — the first pass through 01:30, i.e. still in the pre-transition offset. |
| **Nonexistent** (skipped hour, spring forward) | Resolve to the **first valid instant after the gap boundary**. With 02:00–02:59 skipped, 02:30 resolves to **03:00** local. |
| **Future slot** | Resolve in the **current local timezone**, not the timezone in effect when the row was written. |

The third policy is what keeps travel correct. A slot stored as `08:00`
re-resolves against wherever the user now is, so an 08:00 dose stays an 08:00
dose after a flight rather than drifting to 03:00. This is the whole reason
slots are stored civil rather than as instants (§1) — resolution at read time
is what delivers that promise.

The first two policies are chosen for monotonicity rather than cleverness:
earlier-on-ambiguity and boundary-on-gap together guarantee that resolving an
ordered sequence of civil slots yields a **non-decreasing** sequence of
instants. A dose can therefore never appear to have been due *before* the dose
scheduled ahead of it, which is the property `doseState`, the grace window, and
the edit cutoff all silently depend on.

**Collapsing is expected, not a defect.** Every nonexistent time inside the gap
resolves to the same boundary instant, so on a spring-forward day with
02:00–02:59 skipped, slots at 02:05, 02:30, and 02:59 all resolve to 03:00.
That is what preserves the invariant:

```
01:59  <  {02:00 … 02:59}  =  03:00  ≤  later valid slots
        ↑ skipped hour, all → 03:00
```

Note the shape: strictly increasing into the gap, **equal across** it, then
non-decreasing out of it. Equality is why the invariant is *non-decreasing*
rather than strictly increasing.

Preserving the minutes and shifting by the gap width instead — 02:30 → 03:30 —
would break this. A 02:30 slot would resolve *after* a 03:00 slot scheduled
later the same day, inverting their order and making the earlier dose appear
due second. Resolving to the boundary keeps distinct slots ordered or equal,
never inverted.

Consequences worth stating:

- A 02:30 dose on the spring-forward day resolves to 03:00 — the first moment
  that civil time exists again — so it becomes `due` slightly later in elapsed
  terms than on an ordinary day. It is still exactly one occurrence, and it
  still ages into `missed` normally.
- Two occurrences that collapse to the same instant remain two distinct rows.
  Collapsing affects resolution only; identity stays civil (§1c), so neither
  row is lost, merged, or deduplicated.
- Resolution is a **read-time** operation. No resolved instant is ever stored;
  storing one would freeze a timezone into the row and undo the third policy.
- Both languages implement the same three policies, asserted by the paired
  tests in §8 — including the explicit `02:30` followed by `03:00` case.

## 2. Cross-window synchronization

Same contract as `workspace-changed`, and built the same way rather than
assumed: every mutating command emits **`medicine-changed`**, and every mounted
consumer refetches the authoritative snapshot instead of patching local state.

Consumers: the widget, the Today popup, the medicine popup, the medicine
manager, and the Advanced medicine data panel. Optimistic local state is
allowed only for the in-flight toggle itself — the pattern
[TodayPopupView.tsx:196](../../src/TodayPopupView.tsx) already uses for to-dos,
where the command's returned snapshot replaces local state — never as the
source of truth.

Treatment notes reuse the `expectedNotesRevision` optimistic-concurrency guard
from M17 §2.6, including the separate hydration baseline. Nothing new to design
here; it is a straight port.

## 3. Rust surface

### Modules

| Module | Role |
| --- | --- |
| `medicine.rs` **(new)** | Owns `medicine.json`: entity CRUD, schedule validation, **occurrence generation and regeneration**, dose logging, revision counter, cascade + preflight, due-dose notification. |
| `local_store.rs` | Reused. One change: the `label` parameter in §1g. |
| `external_url.rs` | Reused unchanged, for note links. |

`medicine.rs` gets its own `MedicineState { gate: Mutex<()> }` and its own
`mutate` / `load` / `valid` / `snap` quartet, mirroring `workspace.rs`. The
duplication is intentional: the two stores must not share a lock, or a medicine
write would block a to-do write and vice versa.

### Commands

All mutations return the full `MedicineSnapshot` (including `revision`) and
emit `medicine-changed`.

```
get_medicine_snapshot               // never writes; empty in memory if absent

create_treatment / update_treatment / move_treatment
set_treatment_archived              // { treatmentId, archived }
set_treatment_completed             // { treatmentId, completed }
save_treatment_notes                // { treatmentId, notes, expectedNotesRevision }
open_treatment_note_url

create_medicine / update_medicine / move_medicine
                                    // update_medicine regenerates per §1b
open_medicine_note_url

set_dose_taken                      // { medicineId, slotDay, slotTime, taken }
set_dose_skipped                    // { medicineId, slotDay, slotTime, skipped }

notify_due_doses                    // { graceMinutes } — see §5

// revision-guarded, cascading
get_medicine_delete_impact          // { entity: medicine-store | treatment | medicine, id? }
delete_treatment { treatmentId, expectedRevision }
delete_medicine  { medicineId,  expectedRevision }
delete_all_medicine_data { expectedRevision }
```

**There is no `clear_treatment_dose_history`.** An earlier draft had one, and it
is removed along with its manager control and its tests. A command that strips
history from a treatment you are still keeping is a foot-gun with no honest use
case: the only reason to want it is space, and space is better reclaimed by
saying what you actually mean.

Space is reclaimed by **explicitly deleting a completed or archived treatment**
through `delete_treatment`, after the revision-guarded preflight in §1e. That
path is strictly better: it names the whole thing being destroyed, reports the
medicine and occurrence counts before the user confirms, is already required
for ordinary cleanup, and cannot leave a live treatment with a hole in its
record. One fewer destructive command, one fewer confirmation dialog, and no
way to silently amputate a history you meant to keep.

`create_medicine` and `update_medicine` take the whole schedule as one input
struct and validate it as a unit — times, day pattern, window, treatment-range
containment, and the occurrence caps are not independently valid, so they
cannot be validated independently. Generation happens in the same `mutate`
closure as validation, so a rejected schedule writes nothing.

Note URLs stay revalidated against the saved store immediately before Windows
opens them, exactly as project and to-do notes do today.

## 4. Surfaces

### 4a. Widget destination segment — optional, default off

A third segment inside the existing `.widget-destinations` aside
([WidgetView.tsx:3131](../../src/WidgetView.tsx)), gated by a new
`showMedicinePanel` preference, default **off** so no existing install gains a
segment it did not ask for.

- Content: a medicine glyph, the label **Meds** in Recommended mode, glyph only
  in Compact single-line, and a badge showing doses left today. All taken shows
  a check instead of `0`.
- `data-due` attention tone when a dose is `due` or `missed`, matching how the
  TODO segment already expresses attention.
- Click opens the medicine popup (§4b). With no active treatment, the segment
  shows an empty state and its click opens the manager instead.

**Every widget-facing figure is scoped to `slotDay === today`.** The badge
count, the "N left" count, and the `data-due` attention styling all filter to
occurrences whose `slotDay` is the current local day. This is a hard scope, not
a default:

> A dose missed yesterday, or last week, **never** appears in the badge, never
> contributes to the left count, and **never** applies the attention tone. It
> appears only in the manager's Recent list (§4c).

Without this rule the first missed dose of a course would light the widget red
permanently, since `missed` is terminal — nothing ever clears it, and the user
cannot act on a slot whose day has passed. A permanently-red segment is not an
alert; it is decoration that trains the user to ignore the colour, which
degrades the TODO segment's attention tone sitting beside it.

Today's own missed doses **do** count and **do** apply the tone. The reason is
recording, not prompting: the current day is still open, so the user may still
need to enter what happened for it — taken late, skipped, or left as missed.
The scope is the calendar day, not the grace window.

**Attention here means "today's record is incomplete", nothing more.** The
application must not imply that taking a missed dose late is medically
appropriate — that is a judgement only the user and their prescriber can make,
and this is a tracker, not a source of medical advice (§9). So no surface
prompts, urges, or nudges the user to take a dose. UI copy stays descriptive
throughout: states are **Taken**, **Skipped**, **Missed**, **Due**, and
**Upcoming**; controls are **Take** / **Skip** / **Undo**, which record a fact
rather than recommend an action. Nothing says "don't forget", "you still need
to take this", or "catch up".

§8 carries a regression test for exactly this: a dose missed yesterday must
produce a zero badge, a zero left count, and no `data-due`.
- `data-segments` on the aside currently assumes 1–2; it becomes 1–3, and the
  SCSS in [_widget-core.scss:58](../../src/styles/_widget-core.scss) and
  [_widget-slim.scss:62](../../src/styles/_widget-slim.scss) is updated for the
  third case in both width modes.

**Exact widths** in [widget-layout.ts](../../src/widget-layout.ts).
`widgetDestinationsWidth` gains a `showMedicinePanel` argument;
`widgetFixedWidth` and `widgetWidth` thread it through.

| Mode | Today | Medicine | Projects | All three |
| --- | --- | --- | --- | --- |
| Recommended | 60 px | **+44 px** | 28 px | **132 px** |
| Compact single-line | 33 px | **+33 px** | 33 px | **99 px** |

Recommended medicine is **44 px, not the 28 px this table first specified**. The
Projects segment is a bare glyph pair; the medicine segment carries a glyph, the
**Meds** label, and a dose badge, and 28 px truncates the label. Compact is
unchanged at 33 px because it drops to glyph-only there.

Compact's current expression is `(WIDGET_SLIM_DESTINATIONS_WIDTH / 2) ×
segmentCount`, which yields 33 px per segment. Replace it with an explicit
`WIDGET_SLIM_DESTINATION_SEGMENT_WIDTH = 33` multiplied by the segment count.
Because 66 / 2 = 33, one segment stays 33 px and two stay 66 px: **no existing
layout changes width**, and §8 asserts that as a regression test rather than
trusting the arithmetic.

**Taskbar mirrors need no geometry change — only a regression check.** An
earlier draft claimed "the native DWM destination mirror reads the same
geometry, so nothing drifts." That was wrong, and the correction matters
because it changes what has to be built. The mirrors are not driven by the
width-mode flag or by any layout constant. They are positioned from **measured
live DOM rectangles**: `WidgetView` reads `getBoundingClientRect()` on each
`.widget-app-surface`, converts to offsets relative to `.widget-shell`, and
pushes them to Rust through `set_taskbar_mirror_layout` under a
`ResizeObserver`
([WidgetView.tsx:1266–1309](../../src/WidgetView.tsx)).

Two consequences:

- The mirrors live in the **apps** panel, not the destinations panel, so the
  new segment does not participate in their geometry at all.
- Because measurement is observed rather than computed, mirrors **self-correct**
  when the widget resizes. There is nothing to keep in sync and no second
  source of truth to update.

The requirement is therefore only a **regression check**: toggling the Medicine
segment resizes the widget, and after that resize the taskbar mirrors must
remain aligned to their app surfaces. This is a human-test item (§7, PR 5), not
a code change — a `ResizeObserver` path is not meaningfully coverable by the
model tests in §8.

### 4b. Medicine popup — label `medicine-panel`

Anchored, frameless, always-on-top, `skipTaskbar`, transparent — a direct
sibling of the Today popup, created through the same `todayPopupPosition` /
`createTodayPopupWindow` shape in a new `medicine-panel-window.ts`. Reuses
`useWidgetPanelStyle` so accent and surface preferences apply.

Contents, top to bottom:

1. Header: treatment name, a **Day 3 of 10** label, and the close control.
2. Day progress bar, with a real denominator (§1d).
3. Today's doses: time · name + strength/amount · food hint, each with a check
   control. Taken rows render struck through, matching the existing
   `.today-popup-todos` completed styling.
4. Footer: `2 of 4 taken today` and an icon that opens the manager (§4c).

More than one active treatment shows them stacked, each with its own header and
bar, ordered by `sortIndex`.

**The popup is bounded, and the bound is hard.** It is an anchored overlay that
must fit on the monitor beside the widget, so it cannot grow with the data:

| Bound | Value |
| --- | --- |
| Total visible dose rows | **8**, across all treatments combined |
| Treatment headings | **3** |

- The 8-row budget is shared, not per treatment. Rows are filled in the order
  treatments appear, and once the budget is spent the remaining rows collapse
  into a single **`+N more`** row that opens the manager (§4c) — the same
  affordance and the same wording the TODO section already uses at
  [TodayPopupView.tsx:292](../../src/TodayPopupView.tsx).
- When more than 3 treatments are active, the first 3 render with headings and
  the rest are represented entirely by the `+N more` row. A treatment whose
  rows are all displaced still counts toward `N`.
- `+N more` sits **outside** the 8-row budget — it is chrome, sized like the
  existing `.today-popup-todos__more` row, so eight dose rows plus the more-row
  is the maximum body.

Both numbers are constants beside the Today popup's `TODAY_DOSE_MAX_ITEMS`, and
§8 asserts height derivation at zero rows, at the bound, and past it. Window
height is derived the way `todayPopupHeight` derives Today's, and re-derived
when the snapshot changes — but it is now derived from the *bounded* counts, so
a user with twelve daily doses gets a popup the same size as a user with eight.

| Tab | Content |
| --- | --- |

## 5. Reminders — the live architecture

This mirrors the shipped to-do path exactly, which is: **the widget polls, and
the Rust command sends the toast.** Verified against
[WidgetView.tsx:1190](../../src/WidgetView.tsx) and
[lib.rs:402](../../src-tauri/src/lib.rs).

1. The widget runs a `setTimeout` loop at the existing 30 s poll interval and
   calls `notify_due_doses({ graceMinutes })` only while the preference is on.
2. The command reads a snapshot, computes the notification body from it
   **before** mutating, then marks `notifiedAt` on every eligible occurrence.
3. Only if the revision changed does it send the toast through
   `app.notification()` — Rust-side, via `tauri_plugin_notification` — and emit
   `medicine-changed`.
4. The widget stores the returned snapshot; the emitted event refreshes every
   other open surface.

Because the toast is raised in Rust and not from the webview, **no new webview
notification capability is required** — the existing to-do path works the same
way, which is why `capabilities/default.json` lists no notification permission.
The window-label additions in §4e are still required.

**Notify only inside the grace window.** An occurrence is eligible when
`resolved(slot) <= now <= resolved(slot) + grace` — using the resolved local
instant and the three resolution policies in §1h, because eligibility is an
elapsed-time window — and when it is untouched and its treatment is neither
archived nor completed. Two consequences, both intended:

- A dose whose grace window elapsed while Attention Hub was closed **never
  fires a late toast**. It displays as `missed` and is left alone. This matches
  the lifecycle boundary in [architecture.md](../architecture.md): no
  closed-app reminder service.
- The grace window must exceed the 30 s poll interval by a wide margin or
  eligibility could be missed between polls. The 15-minute floor on the
  preference guarantees that.

**One shared grace value, deliberately.** The same `graceMinutes` drives both
the `due` / `missed` display split in `doseState` and notification eligibility,
so the UI and the notifier can never disagree about which occurrences are live.
Rust clamps the incoming value to the same 15–240 bounds rather than trusting
the webview.

V1 does **not** split this into separate display and notification windows. Two
values would let the widget show a dose as `due` while the notifier had already
written it off, which is the exact class of quiet inconsistency that a single
source of truth exists to prevent — and no user has asked for the asymmetry
yet. If someone later wants a long "missed" threshold with a short notification
window, that is an additive change to a settled model, not a constraint to
design around now.

**The toast names nothing.** Title `Attention Hub`, body
`A scheduled dose is due.` or `N scheduled doses are due.` Not "Attention Hub
Medicine" — a Windows toast can appear on a lock screen and persists in
notification history, and the title is as visible as the body. The to-do path
does put project to-do titles in bodies; this is a considered divergence for
health data, not an inconsistency.

## 6. Privacy and at-rest disclosure

Health data raises the bar above the rest of the app. State all of this in
[architecture.md](../architecture.md) and [privacy.md](../privacy.md), and the
first three points in the `<MedicineDataPanel>` UI itself:

- **`medicine.json` is local plaintext JSON.** There is **no application-level
  encryption** of medicine data in M19, and none is planned as part of it.
- **Its only protection is the Windows user profile** — the app-data directory's
  ACL, plus whatever full-disk encryption the machine already has. Anyone who
  can read the user's profile can read treatment names, medicine names,
  strengths, schedules, and the full dose history.
- **It is excluded from workspace export**, which is the whole reason it is a
  separate file (§1).
- No treatment name, medicine name, strength, schedule, or dose record is ever
  written to diagnostics.
- No notification title or body contains a medicine name (§5).
- No network request of any kind: no drug database, no interaction lookup, no
  spelling suggestions, no icons fetched for medicines.
- No cloud sync, no telemetry, no second person's data.

The disclosure is deliberate rather than buried. A user storing a diagnosis-
revealing medicine name deserves to know the storage model before they type it,
not after.

## 7. Implementation checkpoints

Sequence: **foundation → manager → Today → widget/popup → reminders and docs.**
§0 gates checkpoint 1.

**PR 1–5 below are implementation checkpoints, not a mandated five-PR split.**
They may equally be five commits on one milestone branch delivered as a single
PR. What the numbering fixes is the **order** and the **gates**, not the review
packaging.

The binding rule is: **every checkpoint must independently pass `pnpm test`,
`pnpm build`, `cargo test`, strict Clippy, and `cargo fmt`, and must satisfy its
own stated acceptance criteria, before the next checkpoint begins.** A
checkpoint that only passes once a later one lands has not passed — that is the
failure mode the ordering exists to prevent, and it is equally possible inside
one branch as across five.

Choose the packaging on review load: five PRs if each wants separate scrutiny,
one PR with five green commits if the milestone reviews better whole. Either
way the history must show five points at which the gates were green.

### PR 1 — Data foundation

No user-visible change and no `medicine.json` on disk.

- `medicine.rs`: the full command surface, schedule validation, treatment-range
  containment, **occurrence generation and the §1b regeneration rule**, dose
  logging, revision counter, delete-impact preflight, cascades, notes guard,
  `medicine-changed`.
- The `local_store` `label` parameter (§1g), with `workspace.rs` passing
  `"Workspace"` and a test asserting its nine shipped strings are
  byte-identical.
- `src/medicine-model.ts`: types, slot resolution per §1h, `doseState`,
  progress, today rows, due counting, active treatments, and the editor preview
  expansion.
- **The complete `showMedicinePanel` preference contract**, in
  `widget-preferences.ts`: the field on `WidgetPreferences`, its
  **default-off** value in `DEFAULT_WIDGET_PREFERENCES`, its boolean
  normalization in `normalizeWidgetPreferences`, its participation in the
  existing `WIDGET_PREFERENCES_CHANGED_EVENT`, and its coverage in
  `scripts/test-widget-preferences.mjs`.
- `scripts/test-medicine-model.mjs`, wired into the `pnpm test` chain.
- No UI reads or writes the new preference, and no UI consumes the new
  commands.

**Why the preference lands here and not with its consumers.** Three surfaces
touch `showMedicinePanel` — the manager header (checkpoint 2, reads and
writes), Advanced General (checkpoint 4, reads and writes), and the widget
itself (checkpoint 4, reads). Defining it in whichever checkpoint happens to
touch it first would mean a later checkpoint editing the same normalization
function for the same field, and would put the default-off guarantee — the
thing that protects every existing install — inside a UI checkpoint rather than
the data one. Landing the contract first makes each consumer a pure addition:
**checkpoint 2 adds the manager control that reads and writes it; checkpoint 4
adds the Advanced toggle and is where the widget starts consuming it to show or
hide the segment.**

The preference is therefore live and correct from checkpoint 1, and simply has
no reader yet. That is the same shape as the rest of this checkpoint: complete
contracts, no consumers.

*Accepts when:* installing and running a PR 1 build creates or modifies no
`medicine.json`, `medicine.pending.json`, or `medicine.backup.json`; every
existing workspace error string is unchanged; a stored preference file written
by a pre-M19 build still normalizes with `showMedicinePanel` false; every
existing surface behaves as before; the Rust and model tests in §8 pass.

### PR 2 — Medicine manager

- The `medicine` window: two-column shell, treatment and medicine CRUD, the
  schedule editor with its occurrence preview, the Today tab, the Recent list,
  and the Notes tab (§4c).
- **App routing** branch, **`capabilities/default.json` window entry**, and
  **`_windows.scss` chromed-group entry** for `medicine` (§4e).
- The **Show in widget** control in the manager header (§4c/§4g), using the
  preference contract defined in checkpoint 1. The control **reads and writes
  `showMedicinePanel`** — it must read it to render its own checked state, and
  it round-trips correctly from this checkpoint onward. What waits until

### Checkpoint 6 — Manager design system

Added after the first human review of the Medicine window, which reported that
its controls look unlike the equivalent controls in Project Hub. They do,
and the cause is structural rather than cosmetic.

**Finding.** The two managers implement the same eight patterns twice — shell,
sidebar rows, tabs, row actions, delete confirmation, notes with conflict
resolution, empty and error states, and the inline editor — under different
class names. The icon set is drawn twice: `edit`, `delete`, `archive`, and
`restore` exist in both `ManagerActionIcon` and `MedicineActionIcon` with the
same geometry.

**Root cause.** They are painted from two different palettes. Project Hub uses
the app chrome tokens; `_medicine.scss` defines `--medicine-*` aliases onto the
**widget panel** theme. Surfaces, borders, accents, radii (`--radius-field` 8px
against `--radius-pill` 4px, with `.manager-items` zeroing both) and line
heights all differ.

`_windows.scss` already groups `medicine` with `advanced`, `update`, and
`manager` as a **chromed** window, while `_medicine.scss` paints it with the
theme reserved for frameless overlays. The Medicine manager contradicts the
architecture's own grouping; that is what makes it read as a different product.

**Decisions.**

| Question | Decision |
| --- | --- |
| Palette | Manager-class windows use the **app chrome tokens**. The widget panel theme stays where it was designed to apply: the widget and its frameless popups, including `medicine-panel`. |
| Scope | One shared kit that **both** windows adopt, not a one-way restyle of Medicine. A one-way fix leaves the patterns duplicated and free to drift again. |
| Naming | Reuse the existing `manager-*` class names rather than inventing neutral ones. Project Hub already uses them, they are semantic, and it keeps the churn on the side that is wrong. |
| Sequencing | Before the beta, so the tracker does not ship visibly inconsistent. |

**Work, ordered so each step is separately reviewable.**

1. `src/ActionIcon.tsx` — one icon component covering the union of both name
   sets. Both local copies deleted. Mechanical, and intended to produce no
   visual change.
2. `src/styles/_manager-kit.scss` — the eight shared primitives, expressed in
   chrome tokens, extracted from the current Project Hub rules.
3. Port the Medicine manager onto the kit: drop the `--medicine-*` aliases and
   the widget-panel dependency, adopt the shared classes, and keep only what is
   genuinely Medicine-specific (schedule editor, time chips, weekday picker,
   dose rows). The `medicine-panel` popup is untouched — it is a frameless
   overlay and its widget theming is correct.
4. Port Project Hub onto the kit where it diverges from what was extracted.
5. Fix the defects the review named: mixed radii, solid `+` buttons where the
   equivalent action elsewhere is a text button, and drag handles sitting
   outside the row border.

**Non-goal.** This is not a visual redesign. The target is that the same
control looks and behaves the same in both windows; where the two disagree
today, Project Hub is the reference unless it is the one that is wrong.

## 8. Tests

**`scripts/test-medicine-model.mjs` (new).** `doseState` across all five states
including both sides of the grace boundary; the **preview expansion case table**
for `everyDay`, `everyNDays` (including phase stability from `startOn` when the
window is edited), and `weekdays`, inclusive on both window ends — the same
table the Rust generator is asserted against;

**DST and slot-resolution tests — paired, identical, both languages.** Called
out separately because they are the tests most likely to be written on one side
only, and because they now cover two different mechanisms. All of them are
**deterministic fixtures**: a fixed IANA zone, fixed transition dates, and an
injected "now". **No test — and no human step — mutates the host clock or the
host timezone** (§7).

*Civil behaviour — generation, identity, ordering:*

| Case | Assertion |
| --- | --- |
| Spring forward, slot inside the skipped hour | **exactly one** occurrence on the transition day |
| Fall back, slot inside the repeated hour | **exactly one** occurrence, not two |
| Either transition, slot outside the affected hour | unchanged from a non-transition day |
| Ordering across a transition | `(slotDay, slotTime)` ordering matches calendar order |
| Bare `slotDay` across a transition and a timezone change | still the same `YYYY-MM-DD` |

*Resolution policy — the three rules in §1h:*

| Case | Assertion |
| --- | --- |
| Ambiguous repeated time (fall back) | resolves to the **earlier** occurrence, in the pre-transition offset |
| Nonexistent skipped time (spring forward) | resolves to the **first valid instant after the gap boundary** — with 02:00–02:59 skipped, 02:30 → **03:00** local |
| Collapse across the gap | 02:05, 02:30, and 02:59 all resolve to the **same** instant, 03:00 |
| **`02:30` followed by `03:00`** | both resolve to 03:00 — **equal, never inverted**. This is the monotonicity proof case, and it is the one a minutes-preserving shift would fail by ordering 02:30 → 03:30 *after* 03:00. |
| Collapse preserves identity | two slots resolving to one instant remain **two distinct rows**; neither is merged or deduplicated (§1c) |
| Boundary neighbours | 01:59 resolves strictly **before** the collapsed instant; the first valid slot after the gap resolves at or after it |
| Future slot, timezone changed since it was written | resolves in the **current** zone, so its wall-clock time is unchanged |
| Resolution is total | every civil pair in a year of daily slots resolves without error |
| Monotonicity | resolving an ordered sequence of civil slots yields **non-decreasing** — not strictly increasing — instants across both transitions |
| `doseState` across a transition | `due` / `missed` split falls where elapsed time says, not wall-clock difference |
| Grace eligibility spanning a transition | window measured in elapsed minutes from the resolved instant |
| No stored instant | a round-trip through the store preserves only `(slotDay, slotTime)` |

Both suites assert both tables, so the Rust generator and resolver cannot drift
from the TypeScript preview and resolver (§1h).

**How each side pins the zone.** The two languages need different mechanisms,
and the Rust one constrains the code's shape:

- TypeScript sets `process.env.TZ` around the assertions and restores it in a
  `finally`, which Node honours.
- Rust **cannot** use that route: `chrono::Local` reads the Windows system
  timezone and ignores `TZ`. So `resolve_slot` is split into a
  `resolve_slot_in(zone, …)` that takes the zone as a parameter and a thin
  `resolve_slot(…)` that passes `Local`. Tests call the former with
  `chrono_tz::America::New_York`, which is deterministic on any host. This is
  the only reason the function is generic — and it is a better shape anyway,
  since it makes the "resolve in the *current* zone" policy an explicit argument
  rather than an ambient read.

Neither route touches the host clock or timezone, per §7.

## 9. Non-goals

Refill and stock tracking, adherence statistics or streaks, photographs of
packaging, barcode scanning, drug interaction checking, dosage validation, any

## 10. Deferred, with a required order of operations

**Open-ended treatments.** V1 requires `endOn` because materialized occurrences
need a bounded horizon and progress needs a denominator. Adding open-ended
courses means choosing a rolling generation horizon (say, 90 days forward) plus
a top-up trigger, and deciding what progress means without a total. That
decision should be made deliberately, not by relaxing a validator.

**As-needed (PRN) and every-N-hours dosing.** Both are real, and both were cut
to keep one schedule shape. PRN breaks the "identity is the slot" invariant in
§1c — it needs a nullable `slotTime` or a separate record kind. Every-N-hours
needs an anchor instant per day rather than a fixed time list. Each is a model
change, not a schedule-editor addition.

**Tapering.** A dose amount that changes across the course. Needs `doseAmount`
to move from the medicine onto the occurrence, which is a schema change and a
byte-budget change (§1g).

**The 30-day history matrix** (§4c). Purely additive once the Recent list
exists; it reads the same materialized rows.

**Medicine export / import.** Same discipline as M17 §10 and for the same
reason. Sequence: decide replace-versus-merge → define conflict resolution on
`updatedAt` → decide whether merge needs delete records → if so, add them as
`schemaVersion 2`. Adding delete tracking before merge semantics are specified
is the mistake this section exists to prevent. A medicine export also needs its
own confirmation copy, because the file it writes contains health data in
plaintext (§6) and the user must be told so at the moment they choose the
destination.

**A sound for a due dose.** The meeting-start sound infrastructure would apply
directly, but a second sound source needs a per-source volume story first.

## 11. Resolved decisions

The five questions this section previously held open are now decided. They are
kept, with their resolutions, so the audit can see what was considered rather
than only what was chosen.

**1. Treatment range changes that orphan medicines: superseded during
implementation.**
*Originally resolved as "reject, do not clamp". The implementation took a third
option — deriving the treatment range from its medicines — which dissolves the
question instead of answering it.* Neither rejection nor clamping is needed when
the two ranges cannot disagree. See §1e for the derived rule, its consequences,
and the in-UI copy that states it. The reasoning that rejected clamping still
stands and still applies: nothing silently deletes planned doses as a side
effect of editing an unrelated field.

**2. The 10 000 occurrence cap: keep it, but it is not a size proof.**
*Closed by measurement: see `medicine::tests::byte_budget`, which now fails if
any of these conclusions stops holding.*
*Resolved: retained as a logical cap, with the prospective serialized 4 MiB
check authoritative* (§1g). Measurement replaced the earlier estimate:
≈ 2.689 MiB for 10 000 untouched rows, ≈ 3.109 MiB once touched or notified,
and ≈ 5.812 MiB combined with maximum notes and entity counts. The third case
exceeds 4 MiB, so the caps are **not jointly bounded** and the earlier
"comfortably inside 4 MiB" reasoning was wrong. The pre-write serialized check
is what actually guarantees the limit; 10 000 remains for usability, early
errors, and bounding regeneration work.

**3. The `local_store` `label` parameter: keep it, with regression protection.**
*Resolved: keep the parameter* (§1g). The alternative — a wrapper in
`medicine.rs` that maps errors without touching `local_store` — was rejected
because it collapses nine distinct failure modes into one message, so a user
could no longer be told *which* write step failed. The risk it avoids is
covered instead by the regression test asserting all nine shipped `Workspace`
strings remain byte-identical, plus `write_portable` staying out of scope
entirely.

**4. Grace window: one shared preference in V1.**
*Resolved: a single 15–240 minute value* (§5) driving both the `due` / `missed`
display split and notification eligibility. Splitting it would let the widget
show a dose as `due` after the notifier had written it off — a quiet
inconsistency between two surfaces describing the same fact. Nobody has asked
for the asymmetry; if they do, splitting is additive to a settled model.

**5. `showMedicinePanel` stays off by default, with a visible in-product
control.**
*Resolved: default off, no one-time-hint state.* The discoverability gap is
closed by putting a **Show in widget** toggle directly in the Medicine manager
header (§4c), mirrored with the identical control in Advanced (§4g). Both write
the same preference and both re-render from the same change event.

A one-time hint was rejected on its cost, not its idea: it needs persisted
"have we shown this yet" state, a dismissal path, and a decision about what
resets it — a small state machine whose only job is to apologise for a missing
control. Putting the real control where the user already is removes the need
for the hint entirely.

### Amendment — medicine windows own treatment range

The earlier draft treated treatment dates as a parent constraint and rejected a
medicine window outside them. Human testing showed that this creates an awkward
two-step edit and a blocked treatment form. The model is now reversed:

- A medicine's `startOn` and `endOn` are the editable source of truth.
- A non-empty treatment's start is the earliest `startOn` across its
  medicines; its end is the latest `endOn`.
- Creating, editing, moving, or deleting a medicine recalculates that
  treatment summary in Rust before saving.
- The manager displays treatment dates as a read-only course summary. Empty
  treatments retain their initial finite placeholder range until their first
  medicine is added.

This supersedes the locked-table **Medicine window** rule, §1e's parent-range
validation, the prior rejected-save scenario, and the corresponding draft test
and review-checklist cases. The finite-course requirement remains: every
medicine still has bounded start and end dates.
